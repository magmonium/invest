# invest

Indian market and investment

## What this is

An mm App composed in the `@magmonium/one` visual editor and emitted as a
standalone Angular workspace. It has no Nx workspace behind it —
`@magmonium/one` and `@magmonium/cli` install from the public npm registry.

`.magmonium/` is the **design source**: the Screens, bindings and stores this
code was generated from. Angular markup does not decompile back into any of
that, so an app without it can be run and can never be reopened in the editor.
**Commit it.**

## Run it locally

```sh
npm install
npm start          # compiles mag_assets, then ng serve on :4200
```

To build the way CI does, against the `prod` environment overrides:

```sh
npm run build:wc
```

`mag_assets_env/dev/` is for local testing only and is never deployed. It takes
effect through `patch-wc-env`, which runs inside `build:wc` and nowhere else:

```sh
BUILD_CONFIG=dev npm run build:wc
```

## What you must not edit

These paths are **generated**, and not committed. `npm start`, every
`npm run build*` and `npm test` regenerate them from `.magmonium/` first
(`npm run gen:code`, or `npm run gen:test` for the tests too), and every Save
or Sync from the editor rewrites them:

```
src/app/features/    src/app/pages/       src/app/widgets/
src/app/shared/lib/  src/app/shared/type/
src/app/*.router.ts  src/app/*.provide.ts
```

`.gitignore` excludes them and every file opens with an `AUTOGENERATED`
banner. An edit there lasts until the next `npm start` — change the Screen in
the editor instead.

`@magmonium/cli` is pinned to an exact version on purpose: it is the code
generator, and a different version would build a different app from the same
design. Bump it when the editor tells you the design needs a newer one.

Everything else is yours. `src/app/wc.ts`, `src/app/providers.ts`,
`package.json` and `angular.json` are written once, on the first download, and
the editor never writes them again.

## What the editor cannot draw

`src/app/custom/` is for components the editor has no way to compose — a
chart, a canvas, a third-party embed, anything whose logic is real. Write them
by hand; the editor reads their inputs and outputs and lets a Screen mount one
by name, and it never writes a byte back. See `src/app/custom/README.md`.

## Put it in a GitHub repo

```sh
git init -b main
git add .
git commit -m "Initial commit from the @magmonium/one editor"
gh repo create invest --private --source=. --push
```

Without the `gh` CLI, create the repo on github.com and then:

```sh
git remote add origin git@github.com:<you>/invest.git
git push -u origin main
```

Check before the first commit that `.magmonium/`, `mag_assets/` and
`src/app/custom/` **are** staged, and that `public/assets/` and the generated
paths above are **not** — `.gitignore` already excludes them.

Re-downloading a newer zip from the editor over this folder is safe: nothing in
it replaces a file you have edited.
## Configure before your first release

Register the app in the Magmonium Store first — that is what mints its app id —
and link it in One UI, so every Push writes that id into `.magmonium/index.json`.
CD reads the app id from `appTarget.appId` there, and the backend from
`appTarget.environment.hosts.backendUrl` — the Environment panel's Backend URL.
Pick `dev` or `prod` there before you merge: a `local` one points at your own
machine, which a runner cannot reach, so CD refuses it.

Your deploy token is your own, not the app's: rotate it once from the Store
and reuse it for every app you own or collaborate on. It is the one secret, in
**Settings → Secrets and variables → Actions**:

| Secret | Value |
| --- | --- |
| `MAG_DEPLOY_TOKEN` | Your personal deploy token |

An app made by Extract Plugin has it set for you.

## CI

`.github/workflows/ci.yml`, on a pull request into `main` and nothing else.
It installs from `package.json` alone, regenerates the code, lints, tests, and
builds the web-component bundle with `BUILD_CONFIG=prod`. It never deploys. A
push to a working branch runs nothing.

## CD

`.github/workflows/cd.yml`, when a pull request into `main` merges, and
nothing else — not a push straight to `main`, not a pull request closed
without merging.

It deploys **only when that merge changed `version:` in
`mag_assets/remote/invest.yml`**. Merging is not a release; bumping the version
is. The first merge into `main` is a release all the same: `main` has no
manifest yet, so `version:` goes from nothing to `0.0.1` and CD deploys it.
Register, link and set `MAG_DEPLOY_TOKEN` before that merge.

To release:

1. In One UI, **Push** with **Release needed: Yes** and pick the version change
   (major / minor / patch). The Push writes the new `version:` and ends its
   commit message with `release: <version> (<change>)`. Do not bump the line
   by hand — every Push rewrites the manifest from the editor.
2. Open a pull request from that branch into `main`; CI checks it.
3. Merge it. CD builds and deploys the new version.

The job builds the bundle, `POST`s it to `/store/v1/bundle/<app-id>`, then
`POST`s `/store/v1/deploy/<app-id>`.
